# First workspace increment — shared API contract

All paths below are under `/api/workspace`. Existing Job Tracker login/session and `/api/me` remain authoritative. This development increment runs the actual Job Tracker financial backend in an isolated database; it is not connected to production customer data. `WORKSPACE_ENVIRONMENT=local-pilot` must be visible in the UI when seeded test records are used.

## Roles

`owner` = admin. `rep` = sales. `designer` and new `operations` = scoped back-office access. `crew` keeps existing Job Tracker screens; no CRM access. Reps read owned personal records OR visibility `shared`. Only owner/admin or record owner edits; shared leads require explicit claim. Operations reads the projected request fields, never full sales notes/leads. Admin can use all screens. Job Tracker financial values are read from existing models and `waterfall.compute`, not reimplemented in CRM.

## JSON and routes

Money is decimal string or null. Dates YYYY-MM-DD. Display stages: `New Lead`, `Follow up`, `Design`, `Estimate`, `Ready to Send`, `Awaiting Customer`, `Won`, `Lost`. Work statuses: `Queued`, `In Progress`, `Needs Information`, `Complete`. Fulfillment statuses use existing Job Tracker model.

- GET `/context` → `{environment, finance_source:"Job Tracker", capabilities:{sales,operations,finance}, users:[{id,name,role}], channels:[{id,label,status,detail}]}`. Channels remain explicitly unconfigured; no fake sending.
- GET `/opportunities?scope=mine|shared|all&search=&stage=` → array of allowed opportunity objects.
- POST `/opportunities` → created opportunity. Body: `{name,customer,email?,phone?,address?,visibility?,owner_id?,stage?,amount?,next_follow_up?,work_scope?,notes?}`. Name/customer required; owner defaults current user. Design/Estimate creates request in same transaction.
- GET `/opportunities/{id}` → opportunity with `activities` and `requests` arrays.
- PATCH `/opportunities/{id}` → updated opportunity. Body includes `expected_revision`, `command_id` plus changed fields. Stale edits 409; replay of same command returns prior successful response without duplicate request/audit. Same status save does not duplicate work. Entering Design/Estimate creates or reuses the open request; after completed work creates a new numbered revision on explicit reentry. No deposit gate. No finance job created automatically.
- POST `/opportunities/{id}/claim` → updated opportunity. `{expected_revision,command_id}`. Claim shared record into current rep's private list atomically. Admin may claim own. Reject already-claimed/stale input.
- POST `/opportunities/{id}/activities` → activity. `{kind:"Note"|"Call"|"Email"|"Text",body}` logs an activity only; never sends. For this increment UI should offer Notes and logged call outcomes with clear labels.
- POST `/opportunities/{id}/link-job` → updated opportunity. `{job_id,expected_revision,command_id}`. Match by explicit ID only; rep can link only own financial jobs; owner can link any. Prevent duplicate link to same tracker job from another opportunity. Preserve current finance ownership/values.
- GET `/requests?status=&kind=` → array of scoped operations requests. Admin/back-office sees requests across operations team; sales sees requests for allowed opportunities. Request includes `{id,opportunity_id,opportunity_name,customer,email,phone,address,kind,status,assigned_to_id,assigned_to_name,due_date,scope,result,version,revision,sales_owner_name,linked_job_id,created_at,updated_at}`. No private sales notes/source data. Completed history retained.
- PATCH `/requests/{id}` → updated request. `{expected_revision,command_id,status?,assigned_to_id?,due_date?,result?}`. Back-office/admin only. Complete requires result text and records result for sales. Changes transactional/audited, no finance writes.
- GET `/tracker-jobs` → array of role-scoped existing financial job summaries `{id,name,customer,rep_id,rep_name,status,invoice_total,collected,balance_due,commission_forecast,commission_earned,commission_paid,install_date}`. Sales only own, admin all. Back-office receives status/schedule/name but no commission or costs. `commission_forecast` not payable. Reuse finance source logic and approved eligibility. Null unknown values remain null.
- PATCH `/tracker-jobs/{id}/schedule` → updated scoped job summary. Admin/operations only; `{command_id,expected_status,expected_install_date,status?,install_date?}`. Reject stale old status/date. Allowed statuses are Ordered/Assembled/Delivered/Installed/Punch; financial closure stays with the owner in Job Tracker. Already-closed jobs cannot be changed here. No financial amounts or ownership can be edited.
- GET `/preorder-jobs` → won opportunities without a linked financial job, projected as `{id,name,customer,email,phone,address,scope,sales_owner_name,status,due_date,revision}`. No private notes or money. Back-office/admin sees the queue; sales reads only permitted opportunities. `status` is Prepping or Ready to Order.
- PATCH `/preorder-jobs/{id}` → admin/operations only, `{expected_revision,command_id,status?,due_date?}`. This is a separate operations revision and never changes the sales revision or financial records. Sales context changes, won-stage exit/reentry and job linking invalidate old operations edits. Linked jobs disappear from pre-order preparation and remain available in the Job Tracker fulfillment board.
- GET `/dashboard` → `{pipeline:{count,value,follow_ups_due,by_stage:[{stage,count,value}]},work:{open,design,estimate},finance:{source:"Job Tracker",collected,balance_due,commission_forecast,commission_earned,commission_paid,job_count},team:{collected,job_count},goal:{monthly_target},recent_activity:[]}`. Personal finance strictly scoped; team totals no commission or private lead identifiers. Back-office gets no personal commission values.
- GET `/preferences` → stored JSON object, initially `{}`.
- PUT `/preferences` → stored JSON. Allowed keys: `sales_columns` array, `sales_view` table|kanban, `sales_scope` mine|shared|all, `home_widgets` array, `monthly_target` decimal string. Per-user storage and validation.

Opportunity base fields: `{id,name,customer,email,phone,address,owner_id,owner_name,visibility,stage,amount,next_follow_up,work_scope,notes,revision,linked_job_id,created_at,updated_at}`. Detail activity `{id,kind,body,actor_name,created_at}`. Detail requests use the request shape above. Mutation errors are FastAPI `{detail:"readable message"}`.

`dashboard.finance.collected_this_month` sums received payments dated in the current Phoenix calendar month through today, for the current user's permitted financial jobs. Monthly goal progress uses this field; `collected` remains the all-time total. Changes to sales contact/work-scope/owner fields refresh open request context and increment the request revision; completed request snapshots remain unchanged. Rep-owned shared leads also require an explicit claim before editing.

## Required acceptance

Real authenticated users; persistent leads/views across reload; Rep B denied Rep A private IDs; shared claim is explicit; Design/Estimate immediately in Operations; status repeat does not duplicate; completion returns result to Sales; explicit tracker link displays actual isolated tracker totals; linking and CRM actions never change finance totals; operations never gains owner financial permissions. Test fresh migrations and all original finance tests only against a disposable local SQLite database or verified test Postgres. No credentials from existing apps are loaded.
